## 4. 窗口守卫和退出问题不是同一件事

窗口守卫最初用于在切换目标时自动激活窗口。2026-09-23 的对照确认它会改变激活时序，导致部分模态窗口的控件缓存失效，因此后来默认关闭。部分错误在关闭守卫后仍存在，不能全部归因于它。

2026-10-08 的“重置后仍处于 CU”及指针消失发生时，当前运行时没有守卫。23:38 把脚本重置当作“已释放”缺少依据；23:44 强制结束当轮测试 helper；23:46 用户报告指针消失；之后重载当前 Windows 光标方案恢复可见。

当前官方 sky 服务在脚本内核之外缓存原生客户端。内部客户端有 `closeTransport()`，但安装版本的公开 `sky` 方法及 RPC 分派没有提供对应关闭入口。因此，`js_reset` 和 helper 是否仍存在，都不能单独判断控制已释放。

指针消失紧随强制结束 helper，底层光标机制仍未证明；没有证据把它归因于截图 DLL。后续释放缺口已由源码、官方报告和本机修复对照确认，见第 7 节。采用已有的正常清理请求，保留其他会话的共享 helper。

## 6. Chrome 代理失败的根因和修复

01:13 后的新连接中，Chrome 读取标签和设置会话名仍在约 21–23 秒后返回 `nodeRepl.fetch request failed`。同一机器的 7890 监听正常；父 app-server 有 HTTP/HTTPS 代理环境，已启动的 CUA launcher 和 `node_repl.exe` 没有这些环境变量。

当前浏览器服务先请求 ChatGPT 的身份接口，再加载请求头策略。这个请求使用 Rust `nodeRepl.fetch`，失败的身份 Promise 又会被缓存；Chrome 控制因此在执行页面动作前就失败。本地 IAB 不必走这个外部初始化步骤。显式使用现有代理的匿名请求返回 HTTP 401，说明已到达服务；直连超时。该匿名对照本身不等于认证请求验收。

官方 MCP 启动源码清空子进程环境，再传递基础白名单和显式环境。白名单不含 HTTP 代理。当前桌面端每次启动又重写插件 `.mcp.json` 的 `env_vars`，所以临时修改 manifest 不能持久解决。官方仓库 [#44364 的复现](https://github.com/openai/codex/issues/44364#issuecomment-5902770833)和[两条启动路径的恢复记录](https://github.com/openai/codex/issues/44364#issuecomment-5968902075)与本机证据一致。

本次保留原有启动和导入顺序，只做两项传递：

- 直接 `node_repl`：使用官方系统配置 `%ProgramData%\OpenAI\Codex\config.toml` 的 `[mcp_servers.node_repl.env]`。本机该文件原先不存在；新增现有代理和本地绕过项，没有固定 runtime 路径。
- `cua_repl`：第一阶段在现有 launcher 的 `launch()` 前设置同一环境，保留原文件和哈希。该临时源码改动随后已撤回，由第 8 节的固定启动配置替代。

02:23 用户重启 Codex。02:29–02:30，Chrome 标签清单读取成功；测试会话命名、标签创建、页面状态读取和关闭成功。现有 7129 演示服务已停止，页面显示 `ERR_CONNECTION_REFUSED`，因此这轮没有执行页面内容点击或把该页面判为正常。先前约 21 秒的身份请求失败没有复现。CLI 查询也确认直接 `node_repl` 的代理配置生效；该检查属于配置证据，不单独证明另一条浏览器入口的实机操作。

代理服务和 Windows 系统代理均沿用既有配置。旧的广泛代理注入仍撤销。第一阶段临时改动只能解决当前 runtime，无法满足跨更新维护；用户指出这一缺口后，继续完成第 8 节。

## 8. 代理配置移出运行时

当前 CLI `rust-v0.160.1` 的[插件配置 schema](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/core/config.schema.json)排除插件 transport/env 覆盖；不能通过虚构的插件 `env_vars` 字段解决。其 [MCP catalog](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/codex-mcp/src/catalog.rs)明确普通配置优先于插件默认项。因此使用受支持的完整 `[mcp_servers.cua_repl]` 配置，同名覆盖启动 transport，并保留已有工具范围。

`browser-proxy/persistent.ps1` 在官方系统配置中加入独立配置块，将启动脚本复制到该配置目录。脚本每次读取当前官方 manifest，使用它的 command、args 和环境；通过 `env_vars` 接收父进程的现有代理。额外设置 `NODE_USE_ENV_PROXY=1`，完整保留绕过项。它不固定 runtime 目录，不修改官方 JS，不自行构造 CU helper 协议。标准输入、输出和错误按原字节转发；后端退出码原样返回。

模拟测试确认：保留旧 runtime 文件，同时把 manifest 指向新 runtime，下一次启动确实使用新目录；两次请求在标准输入保持打开时获得响应；代理、自定义绕过地址和官方环境保留；官方 launcher 哈希不变；安装可重复；卸载拒绝改写自己的已变更配置，并保留其他后续编辑。

本机持久配置已安装，CLI 的有效配置指向 `C:\ProgramData\OpenAI\Codex\codex-cu-browser-proxy-launch.ps1`。原 runtime 中的临时代理块已卸载，launcher 恢复匹配的原始文件。固定脚本的只读预检识别到当前 runtime。此处是配置和模拟测试结果；仍需重载后用实际 Chrome 调用确认新入口，不使用旧进程的成功结果替代。

这个方案覆盖已知的 manifest 换路径行为。没有唯一有效 manifest 或启动结构改变时，停止并报告实际错误，不按时间猜目录，不将更新本身判为失效。它不保证未知的未来官方协议改动无需维护。
